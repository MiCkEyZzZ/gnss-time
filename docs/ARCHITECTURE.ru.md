## Слоёная архитектура

`gnss-time` организована в пять слоёв. Зависимости между слоями ацикличны:
каждый слой зависит только от слоёв ниже него.

```text
┌────────────────────────────────────────────────────────────────┐
│  5. matrix         ConversionMatrix, ScaleId — рантайм-        │
│                    интроспекция графа конвертаций              │
├────────────────────────────────────────────────────────────────┤
│  4. convert        IntoScale, IntoScaleWith, ConvertResult —   │
│                    публичное API конвертаций                   │
├────────────────────────────────────────────────────────────────┤
│  3. leap           LeapSecondsProvider, LeapSeconds,           │
│                    RuntimeLeapSeconds — контекстные            │
│                    (с учётом високосных секунд) функции        │
│                    конвертации                                 │
├────────────────────────────────────────────────────────────────┤
│  2. time           Time<S> — основной тип-значение, арифметика,│
│                    конвертации с фиксированным смещением       │
│                    (to_tai/from_tai)                           │
├────────────────────────────────────────────────────────────────┤
│  1. scale + epoch  TimeScale-трейт, маркерные типы (Gps, Utc,  │
│                    …), CivilDate, константы смещений эпох      │
└────────────────────────────────────────────────────────────────┘
```

**Слой 1 (`scale`, `epoch`)** определяет, *что такое шкала времени*: маркерный
тип нулевого размера плюс связь с TAI на этапе компиляции. `epoch`
поставляет арифметику календаря (`CivilDate`), которой выводятся эти связи,
и в остальном не зависит от `scale`.

**Слой 2 (`time`)** определяет `Time<S>` — единый тип-значение крейта, и
всё, что не требует внешних данных: конструирование, арифметика (`+`, `-`,
`checked_add`, …) и конвертации между шкалами с *фиксированным* смещением
относительно TAI (`to_tai`, `from_tai`, `try_convert`).

**Слой 3 (`leap`)** добавляет контекстные конвертации — те, которые зависят
от таблицы високосных секунд, передаваемой в месте вызова (`gps_to_utc`,
`utc_to_gps` и варианты для GLONASS/Galileo/BeiDou, полученные из них). Этот
слой вводит трейт `LeapSecondsProvider` и его две конкретные реализации
(плюс blanket-`&P`-impl).

**Слой 4 (`convert`)** — публичный, эргономичный вход:
`IntoScale`/`IntoScaleWith` оборачивают функции слоёв 2/3 за единым
trait-ориентированным API и добавляют `ConvertResult` для отчёта о
неоднозначности високосных секунд.

**Слой 5 (`matrix`)** — документация в коде: его основная задача — классифицировать
каждую пару шкал (`Fixed`/`Identity`/`EpochShift`/`Contextual`/`SameScale`)
для рантайм-интроспекции и для исчерпывающих попарных тестов, которые
поддерживают достоверность документа. Сам он конвертации не выполняет, с
одним исключением: `beidou_via_gps_to_glonass_via_utc` — реальная цепочка
конвертаций, которая хранится здесь для того, чтобы `ConversionChain` мог
нести промежуточные значения GPS/UTC/TAI, нужные примеру интроспекции.

Два модуля находятся вне этого стека, потому что они опциональны или чисто
аддитивны:

- **`civil`** добавляет человекочитаемое календарное представление
  (`CivilDateTime`) поверх `Time<Utc>`; он не участвует ни в каких
  конвертациях.
- **`serde_impls`** (feature-gated) добавляет `Serialize`/`Deserialize`; он не
  имеет собственной логики конвертаций.

## Модульная структура

```text
src/
├── tables/
│   ├── leap_seconds.rs  — BUILTIN_TABLE (19 записей GPS-эры)
│   └── mod.rs
├── scale.rs         — слой 1: sealed-трейт TimeScale + 6 маркерных типов
├── epoch.rs         — слой 1: CivilDate, константные эпохи, Unix-офсеты
├── time.rs          — слой 2: структура Time<S>, конструкторы, арифметика,
│                      конвертация с фиксированным смещением (to_tai/from_tai),
│                      Unix-методы
├── leap.rs          — слой 3: LeapSecondsProvider, LeapSeconds,
│                      RuntimeLeapSeconds, все контекстные функции конвертации
├── convert.rs       — слой 4: трейты IntoScale / IntoScaleWith + все
│                      реализации по парам шкал, ConvertResult
├── matrix.rs        — слой 5: ConversionMatrix, ScaleId, ConversionKind
├── civil.rs         — CivilDateTime (ISO 8601 / RFC 3339, из Time<Utc>)
├── error.rs         — GnssTimeError (используется каждым слоем)
├── serde_impls.rs   — Serialize/Deserialize для Time<S>, Duration,
│                      DurationParts (только когда feature = "serde")
├── duration.rs      — Duration (интервал со знаком в наносекундах;
│                      не зависит от scale/time — чисто арифметический тип)
├── prelude.rs       — удобные реэкспорты
└── lib.rs           — корень крейта, #![no_std], pub use-реэкспорты
```

`duration.rs` не является частью пятислойного стека выше: `Duration`
представляет *интервал*, а не момент времени, и не имеет никакого отношения
к `TimeScale`. Он используется слоем 2 (`Time<S>`, арифметика), но не зависит
от него.

```text
 └───────────┘   └─────┬─────┘ └─────┬─────┘   зависимостей, кроме взаимной
                       │             │          абстрактности)
                       ▼             │
                 ┌───────────┐       │
                 │    time   │◀──────┘
                 └─────┬─────┘
                       │
                       ▼
            ┌───────────┐   ┌───────────┐
            │   tables  │──▶│    leap   │
            └───────────┘   └─────┬─────┘
                                  │
                                  ▼
                            ┌───────────┐
                            │  convert  │
                            └─────┬─────┘
                                  │
                                  ▼
                            ┌───────────┐
                            │   matrix  │
                            └───────────┘

            ┌───────────┐                  ┌─────────────────┐
  time ────▶│   civil   │◀──── time        │  serde_impls    │────▶ scale
            └───────────┘                  │ (feature=serde) │────▶ time
                                           └─────────────────┘
            (civil не участвует ни в каких конвертациях)
```

Стрелки означают «зависит от». `error` используется каждым слоем (все
операции, которые могут упасть, возвращают `GnssTimeError`) и здесь для
читаемости опущен — кроме случаев, где он сам является листом графа.

Обратите внимание на пару `time` ↔ `civil`: `Time<Utc>` имеет удобный метод
`to_civil()`, возвращающий `CivilDateTime`, а `civil` строит `CivilDateTime`
из `Time<Utc>`. Оба модуля ссылаются друг на друга. Это цикл на уровне
модулей внутри крейта (в Rust допустимый), существующий исключительно ради
удобной функции календарного представления; это не зависимость конвертаций.

## Ключевая инварианта: TAI как центральная точка (pivot) для конвертаций с фиксированным смещением

Любая конвертация между двумя шкалами, каждая из которых имеет **фиксированное**
смещение относительно TAI, проходит через TAI как промежуточное значение:

```text
T_tai    = T_self + S::OFFSET_TO_TAI
T_target = T_tai  - Target::OFFSET_TO_TAI
```

Конкретно это `Time::<S>::to_tai`, за которым следует
`Time::<Target>::from_tai`, скомпонованные в `Time::<S>::try_convert::<Target>()`.
Это значит, что **все** попарные конвертации между шкалами с фиксированным
смещением выводятся из единого согласованного набора смещений относительно
TAI — ошибки на единицу (off-by-one) между отдельными парами шкал
невозможны, потому что ни одна пара не обрабатывается отдельно. GPS ↔ Galileo,
GPS ↔ BeiDou, GPS ↔ TAI, Galileo ↔ BeiDou и Galileo/BeiDou ↔ TAI — это
все *одна и та же* двухстрочная композиция с разными константами.

Две контекстные шкалы — UTC и GLONASS — используют `OffsetToTai::Contextual`,
поэтому у них нет постоянной связи с TAI и они не могут участвовать в
`try_convert`. Тем не менее, конвертация GLONASS ↔ UTC сама по себе является
**фиксированной** на уровне `IntoScale` (см. ниже): GLONASS определён через
UTC(SU) = UTC + 3 ч, это константное смещение эпохи, которое вообще не
проходит через TAI.

Смещения (в наносекундах) — константы времени компиляции, встроены в enum
`OffsetToTai`:

| Шкала   | `OFFSET_TO_TAI`             |
| ------- | --------------------------- |
| GPS     | `Fixed(+19 000 000 000)` ns |
| Galileo | `Fixed(+19 000 000 000)` ns |
| BeiDou  | `Fixed(+33 000 000 000)` ns |
| TAI     | `Fixed(0)`                  |
| UTC     | `Contextual`                |
| GLONASS | `Contextual`                |

Тот факт, что GPS и Galileo имеют идентичное фиксированное смещение, делает
их конвертацию **идентичностью** на уровне наносекунд (см.
`ConversionKind::Identity` в `matrix.rs`) — никакой арифметики не нужно,
только изменение фантомного параметра типа.

## Два класса конвертаций: фиксированные vs контекстные

Каждая упорядоченная пара шкал попадает ровно в один из пяти видов,
классифицированных через `ScaleId::conversion_kind` в `matrix.rs`:

| Вид         | Требует внешних данных?              | Трейт          | Пример                        |
| ----------- | ------------------------------------ | -------------- | ----------------------------- |
| `SameScale` | Нет                                  | не применимо   | `Gps → Gps`                   |
| `Identity`  | Нет                                  | `IntoScale`    | `Gps ↔ Galileo`               |
| `Fixed`     | Нет                                  | `IntoScale`    | `Gps ↔ Tai`, `Gps ↔ Beidou`   |
| `EpochShift`| Нет                                  | `IntoScale`    | `Glonass ↔ Utc`               |
| `Contextual`| **Да** — `LeapSecondsProvider`       | `IntoScaleWith`| `Gps ↔ Utc`, `Gps ↔ Glonass`  |

**Фиксированные конвертации** (`Identity`, `Fixed`, `EpochShift` — в сумме
`ScaleId::is_fixed`) — чистые функции своих входных данных: никакой таблицы
високосных секунд, никакой внешней проверки, которая может завершиться ошибкой;
только переполнение может привести к сбою. Они реализуют [`IntoScale`], чья сигнатура
не содержит такой зависимости:

```rust
pub trait IntoScale<Target: TimeScale>: Sized {
    fn into_scale(self) -> Result<Time<Target>, GnssTimeError>;
}
```

**Контекстные конвертации** требуют знания текущего смещения TAI − UTC, которое
не является константой времени компиляции — оно меняется при каждой вставке
високосной секунды, запланированной IERS. Прятать эту зависимость за глобальным
изменяемым состоянием значило бы сломать поддержку `no_std`, сделать тесты
зависимыми от моков и сделать результат зависимым от того, *когда* был
скомпилирован крейт, а не от явного, проверяемого ввода. Вместо этого каждая
контекстная конвертация принимает `LeapSecondsProvider` явно:

```rust
pub trait IntoScaleWith<Target: TimeScale>: Sized {
    fn into_scale_with<P: LeapSecondsProvider>(self, ls: P)
        -> Result<Time<Target>, GnssTimeError>;
    fn into_scale_with_checked<P: LeapSecondsProvider>(self, ls: P)
        -> Result<ConvertResult<Time<Target>>, GnssTimeError>;
}
```

```rust
// ❌ Скрытое состояние — откуда берутся високосные секунды?
let utc = gps.to_utc();

// ✅ Явный контекст — тестируемо, no_std-совместимо, детерминированно
let utc = gps_to_utc(gps, LeapSeconds::builtin())?;
```

`into_scale_with_checked` дополнительно сообщает, попадает ли результат в
односекундное окно вокруг вставки високосной секунды, через
`ConvertResult<T>`:

```rust
pub enum ConvertResult<T> {
    Exact(T),
    AmbiguousLeapSecond(T),
}
```

За пределами этого окна каждая контекстная конвертация точно циклична
(`A → B → A == A`); внутри его отображение из GPS/Galileo/BeiDou-времени
в UTC не инъективно (две последовательные GPS-секунды могут отобразиться
в одну и ту же гражданскую UTC-секунду), поэтому `Exact` нельзя гарантировать,
и `into_scale_with_checked` существует именно для того, чтобы вызывающий код
мог обнаружить и обработать этот случай, а не молча доверять приближённому
результату.

### Двухпроходный алгоритм UTC → GPS

Наивная конвертация UTC → GPS даёт ошибку ±1 секунда вблизи момента вставки
високосной секунды, потому что коррекция зависит от того, на какой стороне
вставки оказывается *результат* — а это именно то, что вы ещё не знаете.
Библиотека решает это двухпроходным алгоритмом в `utc_to_gps`:

**Проход 1:** TAI вычисляется приближённо, в предположении GPS − UTC = 0.

**Проход 2:** Число високосных секунд, вычисленное на первом проходе,
используется для уточнения результата.

Это устраняет ошибку на границах всех 18 исторических вставок високосных
секунд, покрываемых встроенной таблицей; тестовый набор и фаззинг-цели
`fuzz_gps_utc`/`fuzz_utc_to_gps` проверяют каждую из них.

## Паттерн sealed-трейта

`TimeScale` — sealed-трейт — его нельзя реализовать вне этого крейта:

```rust
mod private { pub trait Sealed {} }

pub trait TimeScale: private::Sealed + Copy + Clone + Eq + PartialEq + Debug {
    const NAME: &'static str;
    const OFFSET_TO_TAI: OffsetToTai;
    const EPOCH_CIVIL: CivilDate;
    const DISPLAY_STYLE: DisplayStyle;
}
```

`private::Sealed` реализован только для шести собственных маркерных типов крейта
(`Gps`, `Glonass`, `Galileo`, `Beidou`, `Tai`, `Utc`), и поскольку `Sealed`
объявлен в приватном модуле, никакой downstream-крейт не может его назвать —
а значит, не может написать `impl TimeScale for MyScale`.

Это осознанный closed-world-дизайн: каждый реализатор `TimeScale` должен
корректно указать свой `OFFSET_TO_TAI` и вписаться в граф конвертаций в
`convert.rs` и `matrix.rs`. Если бы внешние типы могли реализовать этот трейт,
`try_convert::<T>()` пришлось бы обрабатывать шкалы, чьи смещения крейт не
может проверить, и инварианта «все попарные конвертации используют единый
согласованный TAI-pivot» более не могла бы быть проверена собственным
тестовым набором крейта. См. [Расширение](#расширение-добавление-новой-шкалы-времени)
о том, что реально требует добавление *новой, поддерживаемой крейтом* шкалы.

## Представление в памяти

`Time<S>` занимает ровно 8 байт, идентичные голому `u64`:

```rust
pub struct Time<S: TimeScale> {
    nanos: u64,
    _scale: PhantomData<S>,   // ZST, память не занимает
}
```

- Маркерные типы `S` (`Gps`, `Glonass`, …) — Zero-Sized Types.
- Никаких heap-аллокаций в собственном коде крейта (без фичи `serde`; сам
  `serde_impls` тоже не аллоцирует — см. ниже).
- Вся проверка шкал на уровне типов существует только на этапе компиляции;
  в рантайме сверх восьми байт `nanos` ничего не хранится.

Это подтверждается тестом `test_size_equals_u64` в модуле тестов `time.rs` и
size-probe-крейтом `firmware/` (`docs/EMBEDDED.md`), который измеряет
скомпилированный размер `.text` репрезентативных операций на
`thumbv7em-none-eabihf`.

## Архитектура високосных секунд (leap seconds)

Встроенная таблица високосных секунд содержит 19 записей: исходное состояние
GPS-эры (TAI − UTC = 19 с в эпоху GPS, 1980-01-06) плюс 18 последующих
вставок високосных секунд, заканчиваясь TAI − UTC = 37 с (2017-01-01, самая
свежая на момент написания документа). `tables/leap_seconds.rs` встраивает
compile-time-assertions (`const`-блоки), проверяющие, что таблица строго
отсортирована по порогу и что каждая запись увеличивает смещение ровно на 1 —
ошибка во встроенной таблице приводит к падению `cargo build`, а не только
`cargo test`.

Существуют три реализации `LeapSecondsProvider`:

- **`LeapSeconds`** — оборачивает статическую `&'static [LeapEntry]` встроенную
  таблицу (или любой другой `'static`-slice через `from_table`/`try_from_slice`).
  Нулевая стоимость, никаких мутаций в рантайме.
- **`RuntimeLeapSeconds`** — буфер фиксированной ёмкости (`RUNTIME_CAPACITY = 64`),
  без аллокаций, расширяемый в рантайме через `try_extend`, для приёмников,
  которые получают новые объявления о високосных секундах из навигационных
  сообщений. `try_extend` и `try_from_slice`/`from_slice` обеспечивают те же
  порядковые инварианты и шаг приращения в единицу — см. `fuzz_try_extend.rs`
  для fuzz-harness'а,
  который фиксирует этот контракт, включая обнаруженный и исправленный
  `OffsetOverflow` (§ [Фаззинг](../fuzz/README.md)).
- **`&P`** — blanket-`impl<P: LeapSecondsProvider> LeapSecondsProvider for &P`,
  что позволяет передавать ссылку на любую из вышеперечисленных реализаций туда,
  где ожидается аргумент типа provider (например, `gps_to_utc(t, &ls)`).

## Интероперабельность с временем Unix

`Time<Utc>` считает наносекунды от **1972-01-01** (эпоха UTC), тогда как
время Unix отсчитывается от **1970-01-01**. Разница составляет
`UTC_EPOCH_UNIX_OFFSET_S = 63_072_000 с` (730 дней):

```text
unix_seconds    = utc_seconds_from_1972 + UTC_EPOCH_UNIX_OFFSET_S
utc_from_1972   = unix_seconds          - UTC_EPOCH_UNIX_OFFSET_S
```

Это чистое отображение «счётчик ↔ счётчик»: `Time<Utc>` хранит линейный счёт
наносекунд без разрывов из-за високосных секунд. Високосные секунды
применяются только при конвертации между шкалами времени (предыдущий раздел);
Unix-отображение работает исключительно с внутренним линейным представлением
и никогда не обращается к `LeapSecondsProvider`.

| Тип          | Метод                                       |
| ------------ | ------------------------------------------- |
| `Time<Utc>`  | `from_unix_seconds(i64) -> Result<Self>`    |
| `Time<Utc>`  | `from_unix_nanos(i64) -> Result<Self>`      |
| `Time<Utc>`  | `as_unix_seconds() -> i64`                  |
| `Time<Utc>`  | `as_unix_nanos() -> i64`                    |
| `Time<Gps>`  | `from_unix_seconds(i64, P) -> Result<Self>` |
| `Time<Gps>`  | `as_unix_seconds(P) -> Result<i64>`         |

Варианты `Time<Gps>` требуют `LeapSecondsProvider`, потому что они проходят
через `Time<Utc>`, а затем контекстную GPS↔UTC-конвертацию; варианты
`Time<Utc>` этого не делают, потому что не покидают UTC-шкалу.

## Календарная дата-время (ISO 8601)

`civil::CivilDateTime` — человекочитаемое представление, полученное из
`Time<Utc>`: поля год/месяц/день/час/минута/секунда/наносекунда плюс
реализация `Display`, генерирующая текст RFC 3339 / ISO 8601
(`2024-01-15T12:34:56.123456789Z`). Он зависит только от `Time<Utc>` и не
участвует ни в какой конвертации шкал — `to_civil()`/`CivilDateTime::to_utc()`
— это раундтрип без потерь и без аллокаций, который никогда не
обращается к таблице високосных секунд, потому что собственный наносекундный
счётчик `Time<Utc>` уже не содержит разрывов, связанных с високосными
секундами, которые пришлось бы учитывать при отображении на календарные часы.

Как указано в [диаграмме зависимостей модулей](#диаграмма-зависимостей-модулей),
связь между `time` и `civil` на уровне модулей двунаправленная: `Time<Utc>`
получает удобный метод `to_civil()`, а `civil` строится поверх `Time<Utc>`.

### Форматы

`Time<S>` — **человекочитаемый** (JSON, TOML, YAML):

```json
{ "scale": "GPS", "nanos": 1356566418000000000 }
```

Поле `scale` проверяется при десериализации — попытка десериализовать
`{ "scale": "UTC", … }` в `Time<Gps>` возвращает ошибку.

`Time<S>` — **компактный** (postcard, bincode, MessagePack): сырое `u64`
наносекунд без тега шкалы — шкала переносится полностью системой типов,
поэтому на этом уровне нечего проверять или повреждать.

`Duration` и `DurationParts` следуют тому же разделению human-readable/compact:

| `Duration`     | Форма                         |
| -------------- | ----------------------------- |
| Human-readable | `{ "nanos": -7000000000 }`    |
| Compact        | сырой `i64`                   |

| `DurationParts`     | Форма                                  |
| ------------------- | -------------------------------------- |
| Human-readable      | `{ "seconds": 5, "nanos": 500000000 }` |
| Compact             | кортеж из 2 элементов `[u64, u32]`     |

`DurationParts` — отдельный, неотрицательный составной тип (`seconds: u64`,
`nanos: u32`), используемый конструкторами недель/дней GNSS — он никогда не
кодирует знак; отрицательные интервалы существуют только в самом `Duration`.
См. `docs/EMBEDDED.md` для точного формата передачи и таблицы размеров байт.

### Принципы реализации

- **Без proc-macro** — реализации написаны вручную через visitor-API serde,
  поэтому гарантия `no_std` крейта не зависит от предположений о генерации
  кода serde_derive.
- **`no_std`-совместимость** — `serde` подключается с `default-features = false`.
- `is_human_readable()` определяет формат во время выполнения — одна
  реализация работает и с JSON, и с postcard.
- Ошибки проверки шкал не требуют `alloc` — они генерируются через
  `fmt::Display`, а не через форматирование `String`.

```rust
// Пример — JSON-раундтрип
let gps = Time::<Gps>::from_seconds(1_356_566_418);
let json = serde_json::to_string(&gps).unwrap();
// {"scale":"GPS","nanos":1356566418000000000}

let back: Time<Gps> = serde_json::from_str(&json).unwrap();
assert_eq!(gps, back);

// Пример — postcard-раундтрип
let bytes = postcard::to_allocvec(&gps).unwrap();
let back: Time<Gps> = postcard::from_bytes(&bytes).unwrap();
assert_eq!(gps, back);
```

Примечание: сам serde-код `gnss-time` остаётся no_std-совместимым; вызов
`postcard::to_allocvec()` в примере дополнительно требует `alloc` (фича
`alloc` крейта `postcard`).

## Расширение: добавление новой шкалы времени

Добавление шкалы означает добавление нового, внутрикрейтового реализатора
sealed-трейта `TimeScale` через макрос `define_scale!` в `scale.rs`, а затем
включение его в граф конвертаций. Конкретно, для шкалы, чья связь с TAI —
**фиксированное** смещение (наиболее частый случай — см.
[QZSS/NavIC](../docs/GNSS_TIME_PRIMER.md) как разобранный пример,
пункт дорожной карты #TIME-32):

1. **`scale.rs`** — добавить вызов `define_scale!` с параметрами `NAME`,
   `OFFSET_TO_TAI` (`Fixed(offset_ns)` или `Contextual`), `EPOCH_CIVIL`,
   `DISPLAY_STYLE`.
2. **`convert.rs`** — реализовать `IntoScale<NewScale>` для каждой существующей
   шкалы с *фиксированным* offset, с которой она должна конвертироваться
   напрямую (или полагаться на blanket-композицию `try_convert::<T>()` через
   TAI, если прямое, документированное `impl` не требуется). Если новая шкала
   контекстная (как UTC/GLONASS), реализовать `IntoScaleWith<NewScale>` и
   направить через существующую контекстную конвертацию — так же, как
   `Galileo`/`Beidou`→`Utc` идут через `Gps`→`Utc` (см. аудит-исправление
`#TIME-27.1` в `CHANGELOG.md` о том, почему важно направлять через один
   маршрут, осведомлённый о неоднозначности, а не выводить логику високосных
   секунд для каждой шкалы отдельно).
3. **`matrix.rs`** — добавить новый вариант `ScaleId`, расширить `ScaleId::ALL`
   и расширить match `conversion_kind`, чтобы каждая пара с новой шкалой
   была классифицирована. `ConversionMatrix::path_count` и исчерпывающие
   попарные тесты в `matrix.rs` автоматически её включат.
4. **Тесты** — добавить тесты раундтрипа (`new_scale → existing_scale →
   new_scale` сохраняет наносекунды для фиксированных/идентичных связей) и,
   для контекстной шкалы, тест окна неоднозначности по образцу
   `fuzz_gps_utc`/`fuzz_utc_to_gps`.
5. **Документация** — добавить строку в таблицу смещений в разделе
   [Ключевая инварианта](#ключевая-инварианта-tai-как-центральная-точка-pivot-для-конвертаций-с-фиксированным-смещением)
   и в `docs/GNSS_TIME_PRIMER.md`.

Поскольку `TimeScale` sealed, этот список конструктивно исчерпывающий: шкала,
пропустившая шаг 3, просто не появится в `ConversionMatrix`, а собственные
тесты на полноту попарных конвертаций её не обнаружат (они итерируют
`ScaleId::ALL`, поэтому незарегистрированная шкала для них невидима) —
именно поэтому шаг 3 должен быть осознанным, проверенным дополнением, а не
чем-то, что система типов обеспечивает автоматически.

## Ограничения

**Почему нет `From<Time<Gps>> for Time<Utc>`?**

`From`/`Into` в Rust задокументированы как *нефалибельные* и по соглашению
ожидаются как дешёвые конвертации «без возможности упасть». GPS→UTC — не это:
он требует явного `LeapSecondsProvider` (нет дефолтного, до которого трейт
мог бы дотянуться, не возвращая скрытое глобальное состояние, которое этот
крейт сознательно избегает — см.
[Фиксированные vs контекстные](#два-класса-конвертаций-фиксированные-vs-контекстные)
выше), и даже при наличии провайдера результат может оказаться `Overflow`
для значений за пределами представимого диапазона `Time` или неоднозначным
внутри окна високосной секунды. Ничто из этого не вписывается в контракт
`From`, поэтому крейт выставляет `IntoScaleWith`/`gps_to_utc`, которые
делают и требуемый контекст, и возможность сбоя явными в сигнатуре.

Даже конвертации с **фиксированным** смещением (`Gps → Tai`, `Gps → Galileo`,
…) используют `IntoScale`, а не `TryFrom`, по более узкой причине: `TryFrom`
работал бы для *одной* фиксированной пары, но крейту нужен ровно один трейт,
чьи `impl` перечислимы через `ScaleId`/`ConversionMatrix` для истории
интроспекции в слое 5 — смешивание `TryFrom` (фиксированные) и
пользовательского трейта (контекстные) разбило бы эту историю на
«проверь `TryFrom` для этой пары, проверь `IntoScaleWith` для той», без
единого источника правды для «какие конвертации существуют».
`IntoScale`/`IntoScaleWith` дают обоим классам единый вид, который
`matrix.rs` может описать исчерпывающе.

**Другие ограничения, по дизайну:**

- **Нет `PartialOrd`/арифметики через шкалы.** `Time<Gps> - Time<Glonass>`
  не компилируется — сравнение или вычитание через шкалы без явной конвертации
  — это ровно тот класс ошибок, для предотвращения которых на этапе компиляции
  и существует дизайн с фантомными типами.
- **Нет автообновления таблицы високосных секунд.** Встроенная таблица
  заморожена на этапе сборки; приёмнику, которому нужны последние
  объявления IERS, необходимо подставить свой собственный `RuntimeLeapSeconds`
  (см. `docs/LEAP_SECONDS.md` для политики обновления, которая из этого
  следует для мейнтейнеров крейта, и `fuzz_try_extend.rs`/`fuzz_leap_lookup.rs`
  для контракта, которому должна удовлетворять рантайм-таблица).
- **Високосные секунды за пределами последней записи таблицы считаются
  постоянными.** `tai_minus_utc_at` возвращает последнее известное смещение для
  любого TAI-момента после последней записи таблицы, по конвенции IERS
  (никакая високосная секунда не вставляется без ≥6 месяцев предварительного
  уведомления) — это задокументированное предположение, не баг, но это значит,
  что конвертации для дат далеко в будущем молча предполагают «больше никаких
  високосных секунд» вместо того, чтобы выбрасывать ошибку.
- **Нет календарной арифметики на `Time<S>` для GNSS-шкал.** Только
  `Time<Utc>` имеет вид `to_civil()`/`CivilDateTime`; временные метки
  GPS/Galileo/BeiDou/GLONASS должны быть сначала сконвертированы в UTC, если
  нужно календарное представление — снова явный, могущий упасть шаг вместо
  неявного.
